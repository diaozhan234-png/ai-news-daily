LLMs can read and write executables byte by byte from a hex dump
Almost nobody writes machine code by hand. We write source, and a compiler and linker turn it into bytes; to go back, we use disassemblers and decompilers. There are good reasons for this. x86-64 instructions vary in length, jumps are relative byte distances, and one wrong header field means the file won't load. So what can an LLM do with those bytes when it has none of these tools? Takehi et al. recently showed that LLMs can read and write neural network weights directly, which they call Weight-Space Programming . We ask the same question about the other artifact we treat as unreadable output: compiled code. We define Machine Code Programming as a general-purpose LLM reasoning directly about an executable's bytes, with no compiler, assembler, disassembler or execution between it and the file. We test three abilities and one real-world case: Can an LLM work out what a binary does from its bytes alone? We gave the model the hex dumps of three programs we wrote ourselves, plus one real binary from FreeBSD, ministat . The LLM correctly identified what all four programs were, with only their bytes as input . The hardest case is ministat . We built FreeBSD's tool at -O3 , linked it statically against musl, stripped it and removed all of its own text, then hid its last three strings by setting each byte's high bit. The LLM found the decoding loop, recovered the option list and described all eight options . To our surprise, the LLM even found a real bug from the bytes alone , with no access to the source. The binary has no symbols or text explaining the table. Reading the t -table as raw 64-bit floats, it noticed that the option labeled 99.5% confidence uses critical values for about 99.8% , so -c 99.5 applies a stricter test than it claims. We confirmed the bug in the original source code using Claude. For each program we ask for one new feature. The model replies with a list of byte edits, each the same length as the bytes it replaces. Hidden tests then check that the old behavior still works, that the new feature works, and that long inputs are handled correctly. All three patched programs pass every test. How does it do it? Sol 6.1 treats this like a human patching a binary. It finds padding, makes that padding executable by editing the segment headers, writes new code there, and overwrites existing instructions with calls into it. Here is the whole wordcount patch: Now there is no binary at all. This time we ask the LLM to produce a fully functional ELF64 program from a written spec of its behavior. It gets no assembler and no compiler, and must reply with every byte of the file, headers included. All three files ran and matched the reference on every case. Sol 6.1 worked out every jump, call and header field itself, with no assembler. Extending a program used 1.8 to 3.7 times fewer output tokens than writing it. Malware analysts spend hours turning a sample back into assembly or C code with disassemblers and decompilers. We give Sol 6.1 a real sample using the same prompt as Experiment 1, with no hint that it is malicious. It is a 4,608-byte PE32+ file whose only visible import is Sleep . Its other API calls are hidden behind name hashes and its strings are built on the stack. In 211 seconds, Sol 6.1 concluded that it downloads machine code and runs it in memory . Its report named a hardcoded server, 165.154.205.34 on port 443. We then compared it with a public VMRay dynamic analysis of the same file , which we matched by SHA-256. The sandbox contacted the same address, and requested the same URL. We made these comparisons after the run, and they cover one sample and one run. The sandbox confirms the address, the request and the download, but not the 10 s retry or the XOR key itself. Rotate-right-13 hashing is also common in public tooling, so recognition probably helped here too. We did not ask Sol 6.1 to modify malware or write any. These are early results on small programs, but they may soon challenge the foundations of reverse engineering . Disassemblers, decompilers and the assembly they produce exist to turn bytes into something a person can read. In our experiments the LLM didn't need that step: it read, patched and wrote machine code directly. These tools are still essential for human analysts, but for an LLM they may turn out to be optional .
